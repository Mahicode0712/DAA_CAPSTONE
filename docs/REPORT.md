## Phase 1 — Problem design and planning

The program accepts parcels with an identifier, destination node, integer weight, priority score, and deadline. It sorts parcels by earliest deadline and then highest score. A 0/1 dynamic program selects the greatest total score that fits the van capacity. The selected delivery locations are routed through an undirected, weighted, sparse road graph starting and ending at depot node 0.

Parcels are rows in CSV files. Road networks use JSON with named integer nodes and weighted edge triples. `RoadGraph` converts edges into an adjacency list; an edge is stored in both endpoint lists. The supplied generator creates a spanning tree first, so generated road networks are connected, then adds a limited number of random extra roads.

| Algorithm | Purpose | Time complexity | Extra space |
|---|---|---:|---:|
| Merge sort | Stable parcel priority order | O(n log n) | O(n) |
| Insertion sort | Runtime baseline | O(n²) | O(n) |
| 0/1 knapsack DP | Maximum score under capacity C | O(nC) | O(nC) |
| Binary-heap Dijkstra | Single-source shortest paths | O((V + E) log V) | O(V) |
| Nearest neighbour | Approximate stop tour with cached Dijkstra | O(k(V + E) log V + k²) upper bound | O(kV) |
| 2-opt | Improve a closed tour | O(k²) per pass | O(kV) with distance cache |
| Brute-force TSP | Exact small-instance reference | O(k! k) | O(kV) |

Merge sort is chosen instead of quick sort because it guarantees O(n log n) even on an unfavourable input order and is stable. Stability preserves original parcel order when both deadline and value match, which makes the output deterministic and easier to explain. Insertion sort remains useful as a simple baseline but is quadratic.

**Pipeline:** read CSV/JSON → validate data → stable sort → fill the full DP table and trace selected parcels → deduplicate selected stops → compute cached shortest paths → build nearest-neighbour closed tour → expand every tour leg into a road path → report total distance and stage timings.

## Phase 2 — Prioritization and dynamic programming

For item `i` and capacity `w`, the implementation uses the specified recurrence:

`dp[i][w] = max(dp[i-1][w], dp[i-1][w-wt_i] + val_i)` when the item fits, otherwise `dp[i][w] = dp[i-1][w]`.

Traceback compares each row with the preceding row. When the value changes, that parcel is selected and its weight is removed from the remaining capacity. Because every transition uses the preceding row, each parcel is selected at most once.

The hand-checked test uses weights `(1, 3, 4, 5)`, values `(1, 4, 5, 7)`, and capacity 7. Its measured result is **value 9 at load 7 kg**, selecting the weight-3/value-4 and weight-4/value-5 parcels. The tests also compare dynamic programming to exhaustive subset enumeration on 30 seeded random instances and verify the zero-capacity case.

In the generated small-data one-trip run with capacity 60 kg, the planner selects six parcels for **value 409 at load 58 kg**: `P0008, P0012, P0009, P0004, P0010, P0003`. The sorted table and complete result are recorded in [outputs/run_small.txt](../outputs/run_small.txt).

## Phase 3 — Graph processing and route maker

Dijkstra's algorithm uses a binary min-heap. It returns distance and predecessor maps; predecessor links reconstruct an actual shortest road path. Negative road weights are rejected because Dijkstra's correctness requires non-negative weights. If a requested stop is unreachable, route construction raises an error.

Nearest neighbour starts at the depot and repeatedly visits the closest unvisited delivery stop according to shortest-path distance. The source's Dijkstra result is cached so it is reused for every remaining candidate from that current stop. The tour returns to the depot. The displayed road path expands each stop-to-stop leg into the actual shortest-path nodes, not just the abstract visit sequence. 2-opt reverses route sections while reducing length. Brute force checks every permutation only for up to eight stops.

For that same small run, the actual stop order is `Depot → Delivery Point 04 → Delivery Point 03 → Delivery Point 09 → Delivery Point 05 → Depot`, with a total shortest-road-path length of **80.01 km**. The expanded road path is in [outputs/run_small.txt](../outputs/run_small.txt); the large run is in [outputs/run_large.txt](../outputs/run_large.txt). These values are generated by the current code and are not hand-entered examples.

Because this trip has four unique stops, the CLI also checks all stop permutations: its observed nearest-neighbour approximation ratio is **1.000** for this sample.

Charts: [sorting runtime](../outputs/sorting_runtime.png), [runtime per stage (log y-axis)](../outputs/stage_runtime_log.png), and [nearest-neighbour vs 2-opt route length](../outputs/route_length_comparison.png).

In these measurements, insertion sort grows from 0.000049 s at 50 parcels to 0.042016 s at 1600, while merge sort takes 0.001898 s at 1600. Knapsack grows with the number of item/capacity cells (0.024221 s at 1600 items and capacity 200). Dijkstra plus nearest neighbour increases to 0.092487 s for the 400-stop case. 2-opt shortened each measured route: by 2.49 km, 28.56 km, and 82.21 km for 19, 24, and 49 stops respectively. Timings are machine-dependent; in particular, small measurements can vary with background activity.

Possible improvements:

1. A 1-D DP table reduces knapsack memory from O(nC) to O(C), provided capacities are traversed downward; the requested full table is retained here for teaching and traceback clarity.
2. Limit or tune 2-opt work if route sizes grow, or run it only when its quality benefit justifies the extra runtime.
3. Floyd-Warshall can precompute all-pairs shortest paths for small/dense graphs, at O(V³) time and O(V²) space; Dijkstra is a better fit for these sparse graphs.
4. Held-Karp solves TSP exactly in O(k² 2^k) time and O(k 2^k) space, practical only for modest stop counts.
5. Christofides gives a stronger metric-TSP approximation guarantee than nearest neighbour, with additional matching and tree implementation complexity.

## Phase 5 — Results, limitations, and conclusion

The unit suite covers sorting against Python's stable sorted result, hand-checked and randomized knapsack cases, shortest-path reconstruction, unreachable and negative edges, tour validity and length, route comparison against brute-force optimum, 2-opt monotonicity, capacity, and all-trip parcel coverage. Console traces are saved in `outputs/`.

Limitations: the objective prioritizes parcel value but does not model service duration, traffic, vehicle time windows, multiple vehicles, or the possibility of delivering only part of a parcel. The nearest-neighbour route is a heuristic and not guaranteed optimal. The DP table can become large for high capacities. Generated benchmark timings are machine- and load-dependent and should be interpreted as observations rather than universal guarantees.

The capstone integrates sorting, dynamic programming, graph shortest paths, approximation, testing, and empirical runtime comparison in a small standard-library Python application. It is designed so that each algorithm can be explained and tested independently as well as through the end-to-end CLI.
